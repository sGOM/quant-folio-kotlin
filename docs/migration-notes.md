# 마이그레이션 노트 — 원본 동작 보존 기록

설계 §11 원칙: 원본에서 발견한 버그·의심 동작은 **동작을 보존**하고 여기 기록한다. 수정은 컷오버 이후 별도 결정.

예외: 2026-11-07~08 사용자 지시로 주문 안전성 #13·#14를 Kotlin에서 먼저 수정했다. 아래 표는 원본 결함의 이력이며, 이 두 행은 현재 Kotlin 동작이 아니다.
선택 증권사 기준의 실전 게이트, 접수 정보 선저장(호출자 롤백과 분리), 사용자·종목별 접수불명 재주문 차단,
주문번호 누락·HTTP 5xx/408의 접수불명 분류를 적용했다. 잔고 추정 복구는 KIS vts로 한정했다.
즉시 체결 조회는 주문 락 밖에서 하고 반영 직전에 기록 수량을 확인해 체결통보와의 중복을 막는다.
2026-11-08에는 #15②도 수정했다. REST 누적 체결금액에서 해당 주문의 기기록 금액을 차감해 증분 단가를 계산한다.
추가 수량이 있는데 장부 정밀도로 계산한 증분 단가가 0 이하면 장부·상태를 변경하지 않고 다음 정합을 기다린다. 체결통보의 개별 단가 해석은 유지했다.
Python 원본과 과거 장부는 변경하지 않았다. 평균가 누락 시 주문가 폴백과 DB 소수 4자리 정밀도는 유지한다.
#15④도 수정했다. 같은 사용자·전략·종목의 포지션은 DB 트랜잭션 잠금으로 첫 생성과 갱신을 직렬화한다. 잠금을 잡은 뒤 주문의 체결 기록 수량을 다시 확인하고, 초과매도 알림은 체결 기록이 커밋된 뒤 발행한다.
#15③도 수정했다. KIS 체결 조회는 현재 날짜 대신 주문 생성 시각의 KST 날짜를 지정한다. 응답의 주문일이 명시되면 같은 날짜인지 확인한다.
#15①도 수정했다. KIS 모의 잔고 교차확인은 같은 사용자·종목의 매수 체결 수량에서 매도 체결 수량을 뺀 순보유를 사용한다. 장부 순보유가 음수이거나 잔고 조회 전후 매도 기록이 달라지면 해당 잔고만으로 체결을 추정하지 않는다.
Flyway V2는 등록 KIS 계좌나 주문 브로커가 변경되면 해당 사용자의 잔고 기반 추정을 지속 차단한다. 계좌를 되돌려도 자동 해제하지 않는다. 전략이나 주문 이력이 있는 사용자가 처음 자격증명을 등록할 때도 기존 환경 계좌를 사용했을 수 있어 차단한다.
Flyway V3 이후 새 주문에는 주문 클라이언트의 계좌 비교 키를 예약 시점에 기록한다. KIS 모의·실전을 구분하고, 토스는 클라이언트 ID 범위의 계좌 식별자를 쓴다.
환경변수로 계좌를 바꿔도 이전 계좌의 주문을 현재 계좌로 조회하지 않는다. 잔고 추정은 현재 계좌 체결만 합산하며, 사용자의 주문 중 계좌 미상 또는 다른 계좌에 기록된 주문이 하나라도 있으면 잔고만으로는 추정하지 않는다.
기존 주문은 계좌를 추정해 채우지 않는다. 미확인 주문은 수동 확인이 필요하다. V2의 등록 계좌 변경 후 잔고 추정 차단은 유지한다.
Flyway V4부터 포지션은 사용자·계좌·전략·종목별로 분리한다. 기존 포지션에 계좌를 추정해서 채우지 않으며, 주문 판단과 화면의 로컬 잔고에서 제외한다.
평가손익과 포지션 기반 매매 판단은 같은 계좌의 장부로 한정한다. MDD 현금 재생도 새 계좌별 포지션에 실제 반영된 수량만 사용한다. MDD·트레일 고점은 계좌별로 새로 쌓고, 계좌 정보가 없는 기존 Redis 고점과 MDD 발동 상태는 가져오지 않는다.
2026-11-12에는 정합의 접수불명 대상을 주문번호 없는 pending·submitted·partial로 넓혀 신규 주문 차단 집합과 맞췄다. 원본은 잔고로 일부 회수돼 partial이 된 접수불명 주문과 #14④의 submitted·주문번호 없음 주문을 다시 정합하지 않는다. Kotlin의 접수불명 재주문 차단과 겹치면 알림 없이 해당 종목 주문이 멈추므로, 이 주문들도 매 정합에서 잔고 교차확인을 받고 못 밝히면 critical 알림을 낸다.
같은 날 분산 락(`withLockOrElse`)의 해제도 바꿨다. 원본은 값 `"1"`로 잡고 무조건 `delete`하지만, Kotlin은 호출마다 고유 토큰을 값으로 넣고 값이 내 토큰일 때만 지운다. 락 안의 증권사 HTTP가 TTL을 넘겨 락이 만료된 뒤 늦게 끝난 쪽이 다른 보유자의 락을 지우지 않게 하려는 것이다. 키 문자열은 원본과 같다. 만료 뒤 두 보유자가 겹치는 것 자체는 막지 못하며 DB 방어선(멱등 키 UNIQUE, `Fills.record`의 잠금·기록 수량 재확인)에 맡긴다.
2026-11-13에는 세 가지를 바꿨다. 첫째, 주문 예약 때 같은 사용자·계좌·전략·종목에 오늘(KST) 낸 주문번호 있는 submitted·partial 이 있으면 멱등 키가 다른 새 주문도 보류한다. 원본(`executor.py:84-113`)은 멱등 키만 봐서, 앞 주문의 체결이 장부에 오기 전에 손절(`:stop`) 등 키가 다른 신호가 낡은 보유수량으로 다시 주문할 수 있다. 주문일로 한정한 것은 장 마감으로 잔량이 소멸한 주문도 상태가 남아(`cancelled`를 설정하는 곳이 없다) 한정하지 않으면 영구 보류가 되기 때문이며, 이 집합은 `Reconciler`의 open 대상의 부분집합이라 60초 정합이 계속 본다. 둘째, 토큰 발급 락(`cachedToken`)도 값 `"1"`+무조건 `delete`(원본 `kis/client.py:146,165`, `broker/toss.py:94,111`) 대신 고유 토큰+소유자 확인 해제로 바꿨다. 키·TTL(10초)·락을 못 잡으면 최대 4초 기다린 뒤 락 없이 발급하는 동작은 그대로다. 셋째, 주문·포지션 락 TTL을 원본 30초(`executor.py:50`, `base_runner.py:39`, `channels.py:68`)에서 락 안 증권사 HTTP의 코드 상한 합(HTTP 타임아웃·시도 횟수·백오프·throttle 간격 상수에서 유도, 측정값 아님)인 주문 92초·포지션 125초로 늘렸다. 정합 락은 늘렸다가 아래 같은 날 후반 변경(증권사 조회를 락 밖으로)으로 원본 30초로 되돌렸다. 응답 본문 수신, 같은 계좌 키를 쓰는 다른 호출자 뒤의 throttle 대기, DB 잠금·커넥션 풀·Redis 명령 대기는 TTL로 덮지 못해 만료는 여전히 가능하고 DB 방어선이 필요하다. 대가로 보유자가 죽으면 키가 TTL 동안 남고 리밸런싱은 락을 못 잡은 종목을 그 주기에서 건너뛴다.
같은 날 추가로 다섯 가지를 바꿨다. 첫째, 러너가 수량·방향을 정할 때 읽은 이 전략·종목 보유수량을 `place`·`execute`의 필수 인자(`heldQty`)로 넘기고, 예약 트랜잭션에서 미완료 주문 검사 뒤에 읽은 장부(사용자·계좌·전략·종목, 없으면 0)와 다르면 주문을 보류한다(다음 틱이 새 장부로 다시 판단). 원본(`executor.py:77-113`, `rebalance_runner.py:677,1139-1156`)은 판단과 주문 사이에 기록된 체결을 보지 않아 리밸런싱이 락 밖에서 읽은 보유로 이미 체결된 수량을 다시 매수하거나 초과 매도할 수 있다. 검사 순서는 `Fills.record`가 주문 상태와 포지션을 한 트랜잭션에서 커밋한다는 점에 기댄다. 둘째, 주문 POST를 만들기 전 단계(KIS hashkey·토큰 확보, 토스 계좌 검사·토큰 확보)의 실패는 `OrderNotSent`로 올라가 주문을 `rejected`로 확정하고 critical 알림 `order_not_sent`를 낸다. 원본(`executor.py:11-22,128-149`, `kis/client.py:321,351-352`, `toss.py:139`)은 전송 전 실패도 접수불명으로 둔다. Kotlin 에서는 접수불명이 critical 알림과 그 종목 주문 보류를 만들기 때문에, 나간 적 없는 주문을 그 상태로 두지 않으려는 것이다. 증권사의 명시적 거절은 그대로 알림 없는 rejected이고, 인터럽트·주문 POST 자체의 모든 실패·토스 `request()` 안의 토큰 재조회 실패는 접수불명(pending + critical)이다. 대가로 rejected는 멱등 키를 소비해 그 신호(리밸런싱은 그 주기)의 주문이 빠진다. 셋째, 정합에서 잔고 조회 실패(`BrokerError`)와 단가 불명(평균가·주문가 모두 없음)은 보유 없음·접수불명이 아니라 판단 불가로 보고 그 주문을 알림·기록 없이 건너뛰며 `errors`로 센다(잔고 조회 실패는 사용자당 pass에 한 번). 원본(`reconcile.py:150-157`)은 조회 실패를 빈 잔고로 캐시해 접수불명 critical 알림의 근거로 삼고 errors로 세지 않는다. 넷째, 정합의 상태 보정은 증권사 조회 전에 읽은 엔티티를 `save`하지 않고 `update orders set status = :new where id = :id and status = :읽은 값`으로 한다. 락 만료 뒤 체결통보가 만든 `filled`를 `partial`로 되돌리지 않게 하려는 것이다. 다섯째, 체결통보(`FillNoticeApplier`)는 주문 락이 바쁘면 즉시 버리지 않고 250ms 간격으로 최대 20번(약 5초, 측정값 아님) 다시 잡는다. 정합·executor의 DB 반영과 락이 겹쳐 잠시 바쁠 수 있고, 통보는 재전달되지 않으며, KIS 모의 매도는 체결통보가 유일한 반영 경로이기 때문이다. 원본(`fill_notice.py:150-153`)은 즉시 스킵한다. 대가로 그동안 그 사용자의 통보 처리 스레드가 최대 약 5초 멈추고, 5초를 넘기면 여전히 버려진다. 통보 단가가 0이고 주문가도 없으면 기록하지 않는다.
같은 날 이어서 아홉 가지를 바꿨다. 첫째, 정합은 주문별 증권사 근거(체결조회·주문일 주문 목록·잔고)를 락 밖에서 얻고, 락 안에서는 주문 행·기기록 수량을 다시 읽어 증분만 DB에 반영하며 알림은 락을 놓은 뒤 발행한다. 원본(`reconcile.py:269-276`)은 락 안의 `_process_one`(`:223`)이 `get_order_execution`(`:245`)·`get_balance`(`:153`)를 기다린다. 둘째, 주문 하나의 `BrokerError` 가 아닌 예외는 그 주문의 errors 로 세고 다음 주문으로 넘어가며(인터럽트는 전파) 잔고 조회의 그런 실패도 판단 불가로 사용자당 한 번 캐시한다. 원본(`reconcile.py:269-276`)은 try/finally 뿐이라 pass 전체가 중단된다. 셋째, KIS 잔고는 응답 헤더 `tr_cont` F/M 이면 본문 `ctx_area_fk100`·`nk100` 과 요청 헤더 `tr_cont=N` 으로 다음 페이지를 받아 최대 10페이지를 합친다. 상한 초과·규약 위반은 부분 잔고가 아니라 `KisError`, 헤더가 없으면 한 페이지로 본다. 원본(`kis/client.py:421-443`)은 첫 페이지만 읽는다. 넷째, 토스 주문·체결조회·보유 응답은 공식 스펙의 `{"result": {...}}` 봉투가 있으면 벗기고 없으면 최상위에서 읽는다. 원본(`broker/toss.py:210,222,245`)은 최상위만 읽고, 실응답이 어느 모양인지는 미확인이다. 다섯째, 토스 보유 정규화는 스펙 `HoldingsItem` 의 `quantity`/`averagePurchasePrice` 도 읽는다. 원본(`broker/base.py:136,141`)은 `qty`/`avg_price` 만 읽어 토스 보유가 전부 수량 0 이 된다(원본 버그). 여섯째, 주문일 주문 목록 조회(`BrokerClient.dailyOrders`)를 새로 두었다. 주문번호·종목 조건 없이 그 하루를 끝까지 받고 마지막 응답 `tr_cont` 가 D/E 가 아니면(헤더 없음 포함) `KisError` 다 — "없음"이 근거로 쓰이기 때문이다. 주문번호 빈 행은 제외하고(정정·취소 행은 아래 후속 문단에서 표시해 돌려준다) 토스는 미구현이다. 원본은 주문번호 한 건만 조회한다. 일곱째, 체결통보는 `CNTG_YN`=2 이고 `RFUS_YN`≠1 인 통보만 체결로 쓴다. 접수·정정·취소·거부 접수 통보의 `CNTG_QTY` 는 주문수량이라(KIS 공식 예제) 원본(`fill_notice.py:91-115`, 수량 > 0 만 확인)은 접수되는 순간 전량 체결로, 거부 주문도 체결로 기록한다. 또 주문번호로 매칭되지 않으면 같은 사용자·계좌·종목·방향의 오늘(KST) 번호 없는 최근(주문 락 TTL 이내 생성) pending 이 있을 때만 250ms 간격 최대 20번(약 5초, 측정값 아님) 다시 찾는다. 원본(`fill_notice.py:156-164`)은 즉시 버려 POST 응답보다 먼저 온 시장가 체결통보를 잃는다. 반영은 락 안에서 다시 읽은 행으로 하고 주문번호·계좌 키가 바뀌었으면 반영하지 않는다(원본 `fill_notice.py:156-191` 은 락 전에 읽은 엔티티). 수량 해석(증분 = 통보 수량 − 기기록)은 원본과 같은데 `CNTG_QTY` 가 누적인지 건별인지 공식 문서가 밝히지 않아, 판정용으로 모든 통보의 `CNTG_YN·RFUS_YN·ACPT_YN·CNTG_QTY·ODER_QTY·CNTG_UNPR·STCK_CNTG_HOUR` 를 info 로그(`체결통보 수신 odno=…`)로 남긴다. 건별이 사실이면 분할 체결의 뒤 체결이 과소 기록된다(REST 정합이 복구, KIS 모의 매도는 복구 경로 없음). 여덟째, 주문 종결 `orders.closed_at`(Flyway V5)을 두었다. 주문일(KST)이 지난 미완료 주문을 확실한 근거가 있을 때만 종결한다(체결 0 → `cancelled`, 일부 → `partial` 유지 + `closed_at`). 근거는 (가) 주문일 목록에 그 주문번호 행이 정확히 하나(종목·방향 일치)이고 총 체결 == 기록, (나) 목록 행이 없을 때 주문일 뒤 받은 체결조회 누적 > 0 == 기록, (다) 목록 행이 없을 때 KIS 모의 매수 잔고가 "더 배정할 수량 없음"을 확정하는 경우다. 조회 실패·목록 미완결·행 없음·체결 0 은 근거가 아니다. 목록 행의 총 체결 > 기록이면 누적 근거로 증분 반영 뒤 종결하고, < 기록이면 기록을 줄이지 않고 critical `order_fill_mismatch` 를 낸다. 종결은 executions·포지션·`qty` 를 바꾸지 않는 락 안 조건부 update 한 문장이며, 정합 open·stale 쿼리와 `OrderExecutor` 의 unknown·live 술어 네 곳이 모두 `closed_at is null` 로 종결 주문을 뺀다. 접수불명 주문을 종결하면 warning `order_closed_unconfirmed` 다. 원본은 `CANCELLED`(`models.py:46`)를 설정하는 곳이 없고 정합이 SUBMITTED·PARTIAL(`reconcile.py:49,105-110`)과 주문번호 없는 PENDING(`:113-118`)을 영원히 다시 본다. 이 근거 목록은 아래 후속 문단에서 넓어졌다(모의 매도·토스 종료 상태·접수불명 목록 근거). 그래도 근거가 없는 주문은 종결되지 않고 계속 정합 대상이다. 아홉째, 접수불명 주문번호 회수다. 주문일 주문 목록에서 종목·방향·주문수량이 같고 주문 시각이 주문 행 생성 시각의 −2초~+120초(측정값 아님) 안이며 같은 사용자·계좌·주문일의 다른 주문에 붙지 않은 번호의 후보가 정확히 하나일 때만 조건부 update 로 붙이고(pending → submitted) 그 pass 는 끝낸다. warning 알림 `order_number_recovered`. 후보 0·복수·목록 미지원·조회 실패면 기존대로 잔고 교차확인 → 접수불명 알림이며, 회수·종결 경로에서 주문 전송은 없다. 한편 주문 POST 의 연결 수립 실패(`ConnectException` 등)는 미전송으로 분류하지 않고 접수불명으로 두기로 했다 — 요청 전 실패임은 구현 세부일 뿐 공개 계약이 아니고, 재사용 연결 실패는 요청 도착 여부와 무관하게 같은 `IOException` 이라 줄어드는 접수불명이 적다.
이후 정합의 종결·알림을 다음과 같이 바꿨다(원본 `engine/reconcile.py`·`broker/kis.py`·`broker/toss.py` 와 다른 동작). 첫째, KIS 주문 목록의 정정·취소 행(`orgn_odno` 있음)을 버리지 않고 `originalOrderNo`(trim 원문, 정규화 없음)로 표시해 돌려준다. 주문번호 회수 후보와 "이 주문번호의 행"은 원주문 행만 쓰고, 원주문번호 사슬(문자열 일치, 정정의 정정 포함)로 이어진 정정·취소 행의 체결 합이 0 보다 크면 자동 기록·종결 없이 critical `order_modified_externally` 로 사람에게 넘긴다(원본은 주문번호 한 건만 조회해 정정 체결을 보지 못한다). 둘째, 접수불명 주문은 주문일이 지났고 완결된 주문일 목록에 증인(같은 사용자·계좌·주문일의 다른 주문에 붙은 번호의 원주문 행)이 있으며 같은 종목·방향의 주인 없는 행이 없으면 목록 근거로 종결하고 warning `order_closed_unconfirmed` 를 낸다(잔고가 체결을 배정했거나 판단 불가인 pass 는 제외). 원본은 접수불명 주문을 영원히 다시 본다. 셋째, KIS 모의 매도는 주문일이 지난 뒤 잔고 보유수량(없으면 0) == 장부 순보유일 때만 종결 근거로 쓰고(종결 직전 사용자 행 잠금 아래 계좌 재확인) 매도 체결을 잔고로 추정해 기록하지는 않는다 — 원본도 매수만 추정한다. 같은 종목의 미기록 매수와 미기록 매도가 같은 수량이면 구분하지 못한다(기존 매수 경로도 같은 구멍). 넷째, 토스 체결조회 결과에 `Fill.terminal` 을 새로 두었다(원본 `toss.py` 에 없는 필드). 공식 스펙 `OrderStatus` 가 FILLED·CANCELED·REJECTED 이고 `filledQuantity` 를 0 이상의 정수로 읽었을 때만 true 이며 REPLACED·`*_REJECTED`·진행 중·모르는 값은 false 다. 주문일이 지난 주문이 terminal 이면 누적 == 기록(0 포함)일 때 종결하고 누적 < 기록이면 `order_fill_mismatch` 다. KIS 는 항상 false. 다섯째, 주문일이 지났는데 한 pass 에서 진전(종결·회수·체결 기록·상태 보정) 없이 끝난 주문은 메모리 맵으로 3600초(`PAST_DAY_RECHECK_SECONDS`) 뒤까지 증권사 조회를 건너뛴다(락 바쁨·오늘 주문 제외, 재시작하면 맵이 비어 한 번 더 확인). 재확인에서도 미해결인 주문번호 있는 주문은 관측 사실만 담은 critical `order_unresolved`(24시간 dedup)를 낸다. 원본은 매 주기 조회하고 주문번호 있는 주문은 알림이 없다. 3600초·24시간은 측정값이 아니다. 실응답으로 확인하지 못한 가정: KIS `orgn_odno` 가 `odno` 와 같은 표기인지(다르면 사슬이 이어지지 않아 원주문 행만으로 판단 — 이전과 같은 동작), 취소 행의 수량 모양, 모의투자 주문 목록이 실제로 행을 돌려주는지(원본 관찰은 늘 빈 응답), 토스 `status` 실값. 여섯째, 엔진 제어 채널에 `resolve_order` 액션을 새로 두었다(원본은 start/stop 만 받는다). 자동 정합이 근거를 못 얻어 사람에게 넘긴 주문을, 사람이 증권사에서 확인한 최종 누적 체결(`filled_qty`·`avg_price`)과 종목(`symbol`)으로 장부 반영과 종결까지 한 트랜잭션으로 처리한다(`Reconciler.resolveManually`). 주문일(KST)이 지난 주문만, 기록을 줄이지 않는 방향으로만 받고 조건이 하나라도 어긋나면 아무것도 바꾸지 않고 warning `order_resolve_rejected` 를 낸다. 성공은 warning `order_resolved_manually`. 엔진은 입력값을 증권사에서 검증하지 않으며 증권사 조회·주문 전송이 없다. 불변식은 `trading-safety.md`, 절차는 컷오버 런북 "운영 중 수동 조치".
2026-11-16 KIS 모의 실측(아래 "KIS 실측" 절)으로 세 가지를 더 바꿨다. 위 2026-11-13 문단의 체결통보 락 재시도(다섯째)와 수량 해석(일곱째의 "증분 = 통보 수량 − 기기록"), 2026-11-13 이후 문단의 미확인 가정 중 `orgn_odno` 표기·취소 행 모양·모의 주문 목록 행 유무는 이것으로 대체·확인됐다. 첫째, 체결통보는 장부에 수량을 쓰지 않고 매칭된 주문 하나의 정합(`Reconciler.reconcileOrder` — 주기 정합과 같은 처리, 대상도 같은 open 술어)만 트리거한다. 실측에서 `CNTG_QTY` 는 체결 건별(300주 시장가 매수의 통보 14건 합 = 주문 목록 총 체결 50)이었고 체결 고유번호가 없으며 같은 초·같은 수량·단가의 별개 체결 통보가 연달아 왔다. 원본(`fill_notice.py`)처럼 누적으로 보고 빼면 두 번째 체결부터 버려지고, 건별로 더하면 정합이 REST 누적으로 이미 반영한 체결의 늦은 통보를 가를 키가 없어 이중 기록이 된다. 수량·단가는 단건 체결조회 누적에서 기기록 대비 증분으로만 쓴다(통보 단가는 쓰지 않는다). 통보의 락 재시도는 없앴다 — 락이 바쁘면 넘기고 60초 주기 정합이 잡는다. 통보 직후 조회가 그 체결을 아직 포함하지 않는 경우도 주기 정합에 맡기며, 그 지연은 측정하지 못했다. 둘째, KIS 단건 체결조회 TR 을 원본 `TTC8001R` 에서 `TTC0081R`(쿼리에 `EXCG_ID_DVSN_CD=ALL` 추가)로 바꿨다. 모의 `VTTC8001R` 은 전량·부분 체결 주문 모두 `rt_cd=0`·`msg_cd=70070000` "조회할 내역 없음"·행 0개라 체결 0 으로 읽혔고(원본 주석 "모의는 늘 빈 응답"의 실체), `VTTC0081R`+`ODNO` 는 그 주문의 행 하나를 돌려줬다. 실전 `TTTC8001R` 의 동작은 측정하지 못했고 KIS 공식 샘플은 3개월 이내 조회에 `TTC0081R` 을 쓴다. 잔고 교차확인 등 조회 0 에 대한 방어는 그대로다. 셋째, KIS WebSocket 기본 주소를 원본 `wss://ops.koreainvestment.com:31000`·`:21000` 에서 `ws://ops.koreainvestment.com:31000/tryitout`(모의)·`ws://ops.koreainvestment.com:21000/tryitout`(실전)으로 바꿨다. wss 는 두 포트 모두 TLS 핸드셰이크가 실패했고 모의 ws+`/tryitout` 은 구독·통보 수신을 확인했다. 실전 주소의 접속은 측정하지 못했다.

## KIS 실측에서 확인한 접속 문제 (2026-11-16)

원본 `backend/app/core/config.py`와 Kotlin `QuantfolioProperties.Kis`의 모의 WebSocket 기본값은
`wss://ops.koreainvestment.com:31000`이다. 실측에서 TLS handshake가 실패했다.
[공식 설정](https://github.com/koreainvestment/open-trading-api/blob/main/kis_devlp.yaml)은 `ws://…:31000`이고,
[공식 실행 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_user/domestic_stock/domestic_stock_examples_ws.py)는 `/tryitout`을 붙인다.
처음에는 확인 도구(`KisProbe`)에만 이 주소를 명시했고, 이후 같은 날 운영 기본값도 이 주소로 바꿨다(위 2026-11-16 문단 셋째).
수정한 주소에서도 초기 JDK 연결은 `HTTP/1.1 header parser received no bytes`로 실패했다.
설치된 Node `ws`로 접수 통보를 받은 뒤 그 연결이 종료되고, 11:45:35 KST에 JDK로도 구독 성공 응답과 AES 키를 받았다.
초기 연결 종료 원인은 미확정이다. 이후 JDK `KisSocket` 으로 `ws://…:31000/tryitout` 에 접속해 40분간 통보를 받았다.
실전 `ws://…:21000/tryitout`·경로 없는 `ws://…:31000` 은 측정하지 못했다. 원본 `.env` 의 `KIS_WS_URL_*` 는 Kotlin 이 읽지 않는다(`quantfolio-core.yml` 에 매핑 없음).

이번에 고치지 않은 실측 관찰(같은 날, 기록만):

- `rt_cd="2"` 가 실재한다 — 잔고 GET 에서 계좌·앱키 불일치 시 `OPSQ2000 INPUT INVALID_CHECK_ACNO`. 주문 POST 에서는 보지 못했다.
  주문 POST 의 명시적 거절(`rt_cd="1"` `40070000` 매매불가 종목)은 `KisError` 로 거절 처리됐다. 모의투자 매매불가 종목이 있다(예: 252670).
- 잔고 GET 첫 호출에서 `HTTP 500` `rt_cd="1"` `EGW00215`(원장 초당 거래건수 초과) 1회, 재현 안 됨. 코드는 `EGW00201` 만 재시도한다.
- 계좌 미신청·만료는 `rt_cd="1"` `41100000`("모의투자 신청내역을 확인하세요"), 토큰 재발급 분당 1회 초과는 `HTTP 403` `EGW00133`.
- 정상 주문 응답은 `rt_cd="0"`, `output`={`KRX_FWDG_ORD_ORGNO`("00950"), `ODNO`(10자리 0 채움), `ORD_TMD`}.
  구 TR `VTTC0802U`·`0801U`·`0803U` 는 모의에서 동작한다(공식 샘플은 신 TR `0012U`·`0011U`·`0013U`).
- 시장가 1주 주문의 체결 통보가 접수 34초 뒤에 왔다. 부분 취소 뒤 체결 통보의 `ODER_QTY` 는 300 → 50 으로 줄었다(주문 목록 원주문 행 `ord_qty` 는 300, `rmn_qty` 만 줄어듦).

## 의도적 차이 (동작 동등, 표현만 다름)

- 422 검증 오류 `msg` 는 pydantic 영문 대신 한국어/Bean Validation 메시지.
- `representative()` 메시지의 원인별 건수 표기 형식(`{A=1}` vs `{'A': 1}`).
- 성과귀속 롱숏(`Attribution.factorAttribution` 의 `ls_return`): 원본 `pair.sort_values(ascending=False)` 는 numpy quicksort 라
  **동점 순서가 구현(CPU SIMD 경로)마다 다르다.** Kotlin 은 안정 정렬. `score` 가 소수 4자리 반올림이라 실데이터에서
  상·하위 1/3 경계에 동점이 걸리면 값이 갈린다(2층 정답지에서 1건 관측). IC(평균순위)·매매 결정(안정 정렬 `list.sort`)은 무관.
- 스크리너 라우트 캐시: 원본은 Redis 조회 실패 시 500, Kotlin 은 다른 지표 라우트처럼 캐시 미스로 보고 계산(`JsonCache`). Redis 장애 때만 다르다.
- `/ws` 인증 실패: 원본은 accept 전에 close(4401) 해 uvicorn 이 핸드셰이크 403 으로 응답 → 브라우저엔 1006 이라 프론트의 4401(로그인 이동) 분기가 동작하지 않고 재연결을 반복했다. Kotlin 은 accept 후 4401 로 닫아 프론트 계약대로 동작한다.
- 뉴스 HTML 엔티티: 원본 `html.unescape` 는 HTML5 이름 엔티티 2,231개를 모두 푼다. Kotlin `NewsFeeds.htmlUnescape` 는 숫자 엔티티 전부 + 뉴스에 쓰이는 이름 44개만 — 표에 없는 드문 이름 엔티티는 원문 그대로 남는다(요약 표기만 다름).
- 뉴스 전체 실패 알림 문구의 확인 위치: 원본 `app/services/news.py::FEEDS` → `NewsIngestor.FEEDS`(이전 후 실제 위치).
- 워커 DB 대기(`wait_for_db`)는 옮기지 않았다 — Spring 은 기동 시 DB 연결(JPA 스키마 검증)을 요구하고 실패하면 컨테이너 재시작 정책으로 재기동된다. 원본처럼 "DB 없이 기동"하지 않는다.
- 엔진 제어 채널: 원본은 pubsub 폴링 루프가 실패하면 재구독하며 3회 연속 실패 시 경보. Kotlin 은 `RedisMessageListenerContainer` 가 재연결을 맡아 그 경보가 없다(연결 장애는 heartbeat·web 헬스로 드러난다).
- 접수불명 알림의 원인 표기 `{e!r}`(Python repr) → Kotlin `e.toString()`(예외 클래스명 + 메시지). 표기만 다름.
- `RebalanceRunner.preview()`(원본 스크립트용 미리보기)는 옮기지 않았다 — 호출하는 라우트·스크립트가 없다.
- 배포: 원본 `docker-compose.override.yml`(uvicorn `--reload`)은 옮기지 않았다 — JVM 에 해당 없음. 소스 볼륨 마운트(`./backend:/app`)도 제거(이미지에 jar 포함).
- 배포: worker 가 원본은 redis 만 기다렸지만 Kotlin 은 `web` healthy(=Flyway 완료) 뒤에 기동한다. engine 도 같다.
- frontend `Dockerfile`: 원본 `npm install`(lockfile 미사용)은 현재 레지스트리에서 `edgesOut` null 오류로 재현 가능하게 실패 → `package-lock.json` + `npm ci`. 앱 코드는 무수정.
- e2e-smoke: 원본은 시크릿 파일 11개만 만들어 `s3_backup_*` 누락으로 compose 가 기동하지 못했을 것 — 13개 모두 생성. `alembic upgrade head` 단계는 web 기동 시 Flyway 로 대체.
- Caddy 의 `/docs`·`/openapi.json`·`/redoc` 라우트는 남겼지만 Kotlin web 은 해당 문서를 제공하지 않는다(404).
- 요청 DTO 의 `@Size`(전략 이름 255·설명 2000·닉네임 50·비밀번호 8~128)는 UTF-16 단위, 원본 pydantic 은 코드포인트 단위 — 이모지 등 보조 평면 문자로 한도 근처를 채운 입력만 판정이 갈린다. 전략 설정(config) 검증기는 코드포인트로 맞췄다.
