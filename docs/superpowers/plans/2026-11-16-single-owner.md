# 단일 소유자 거래 전환 Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development to implement the task and review it.

**Goal:** 증권사 자격증명은 서버 시크릿 설정에서만 읽고, 계정 선택 없이 접속 비밀번호만 사용하는 개인 서비스로 전환한다.

**Architecture:** 기존 `BrokerCredentials`와 서버 세션을 재사용한다. 기존 사용자 ID와 비밀번호 해시는 내부 데이터 연결·인증에 유지하고, API·엔진·주문은 그 소유자로 한정한다.

**Tech Stack:** Kotlin, Spring Boot, PostgreSQL, Redis, Next.js.

## 근거와 범위

Claude 마지막 사용자 답변(2026-11-16): “혼자 쓰는 서비스임”. 앞선 제안의 1단계(서버 설정 단일 출처 + 소유자 거래 제한)를 이어간다.
DB 자격증명 우선순위 때문에 최신 시크릿이 무시되고 다른 사용자도 소유자 계좌를 사용하는 문제를 없앤다.
추가 확인(같은 날): 사용자는 계정의 필요성을 물었고 “접속 비밀번호만 유지”를 선택했다. 이메일 입력·회원가입·계정 선택은 없애고 기존 운영 비밀번호와 세션을 유지한다.
자격증명 등록 API와 DB 컬럼·트리거의 물리 삭제는 후속 단계다. 기존 등록 API가 성공한 것처럼 보이거나 사용하지 않는 키를 저장해서는 안 된다.
후속 단계 완료(2026-11-17): 등록 API·`users` 자격증명 컬럼·V2 트리거(Flyway V6)·`CredentialCipher`·`credential_enc_key` 삭제, 잔고 추정 차단 표시는 유지.

## Global Constraints

- 기존 미커밋 KIS 수정·테스트·문서·프론트 의존성 변경을 보존한다. 커밋·푸시하지 않는다.
- 시크릿 파일은 읽어 출력하거나 편집하지 않는다. 원본 `quantfolio` 스택·DB를 변경하지 않는다. 증권사 주문을 전송하지 않는다.
- `TRADING_OWNER_USER_ID`는 nullable 양의 사용자 ID다. 미설정이면 거래와 소유자 자격증명 접근을 차단한다. 소유자를 첫 가입자 등으로 자동 선택하지 않는다.
- 기존 운영 데이터의 사용자 ID 1을 내부 소유자로 이어받는다. 사용자는 계정 ID를 선택하지 않는다. 실제 설정은 격리 스택 `.env`에만 적용하고 원본 DB·비밀번호는 변경하지 않는다.
- 서버 설정(configtree 시크릿 우선, 기존 환경변수 호환)은 유지한다. DB 키·시크릿·계좌는 주문 및 시세 클라이언트 생성에 쓰지 않는다.
- 기존 계좌 키 대조, 접수불명 주문 재전송 금지, KST 날짜, 실전 승인 게이트를 유지한다. 원본 동작과 달라지는 부분은 문서에 기록한다.
- 비소유자는 전략 시작, 복구, 직접 주문 실행 및 소유자 잔고·자격증명 사용을 할 수 없다. 정합이 다른 사용자의 주문에 소유자 계좌를 배정하지 않는다.
- API 필드 이름과 로그인은 유지하되 자격증명 상태·계좌 표시를 실제 서버 설정과 일치시킨다. 비소유자에게 소유자 계좌를 노출하지 않는다.

## Task 1: 서버 설정 기반 소유자 거래 제한

관련 파일: `BrokerCredentials.kt`, `QuantfolioProperties.kt`, `quantfolio-core.yml`, `EngineControllers.kt`, `EngineRuntime.kt`, `OrderExecutor.kt`, 필요 시 `Reconciler.kt`, `AuthDtos.kt`, `StrategiesController.kt`, frontend 설정 화면, `.env.example`, compose 환경 전달, 해당 테스트·규칙·이전 기록.

- [x] 호출자와 테스트를 조사하고 소유자 판정을 공통화한다. 새 권한 계층·역할 체계는 만들지 않는다.
- [x] DB 키가 남아 있어도 서버 설정이 사용되는 테스트, 미설정·비소유자 차단, API 시작·엔진 복구·직접 주문의 부작용 없음 테스트를 먼저 추가하고 실패를 확인한다.
- [x] 최소 구현으로 위 테스트를 통과시킨다. KIS와 토스 시세 모두 DB 자격증명을 무시한다.
- [x] 등록 API는 명확히 거부하고 설정 화면은 서버 관리 상태와 연결 확인을 표시한다. 기존 API 필드와 보유 데이터는 보존한다.
- [x] 기존 관련 테스트·픽스처를 새 계약에 맞추고 전체 빌드, 프론트 테스트·타입·lint·빌드를 검증한다. (프론트 `npm run build` 는 이번 변경 뒤 미실행 — tsc·vitest·lint 만 통과)
- [x] 관련 문서, `.env.example`, compose 설정을 갱신하고 독립 리뷰·`doc-check`·문서 린트를 마친다. (`doc-check` 스킬 미실행 — 독립 리뷰·문서 갱신·md 린트만 완료)

검증은 가짜 증권사와 Testcontainers를 사용한다. 격리 스택 재배포는 소유자 지정 및 검증 완료 후 결정하며, 자동매매 전략을 시작하지 않는다.

## Task 2: 계정 선택 없는 비밀번호 접속

- [x] `/api/auth/login`은 비밀번호만 받아 설정된 내부 소유자의 기존 비밀번호 해시를 검증한다. 클라이언트가 보낸 username으로 다른 사용자를 고르지 않는다. 미설정·소유자 행 없음은 명확히 실패하고 계정 생성·암호 재설정을 하지 않는다.
- [x] 회원가입 API를 거부하고 로그인 화면의 이메일·회원가입 UI 및 사용하지 않는 클라이언트 가입 함수를 제거한다. 세션 쿠키·로그아웃·로그인 시도 제한은 유지한다. 시도 제한의 사용자 키는 입력 username으로 바꿀 수 없어야 한다.
- [x] 기존 비소유자 세션을 HTTP와 WebSocket 모두 거부한다. 가능하면 공용 세션 조회 경로에서 처리하고 중복 권한 계층을 만들지 않는다.
- [x] 실제 소유자 비밀번호 성공·오류·소유자 없음, 회원가입 거부, 다른 username으로 선택 불가, 기존 비소유자 세션 거부, 시도 제한 우회 불가 테스트를 먼저 실패시킨 뒤 구현한다.
- [x] 기존 컨트롤러 테스트의 사용자·세션 픽스처와 로그인 UI 테스트를 새 계약에 맞춘다. e2e는 신규 가입 대신 명시한 스모크 비밀번호를 사용하고 비밀번호 미설정은 사유와 함께 skip한다. 기존 전략을 수정하지 않으며 생성한 스모크 전략만 정리한다.
- [x] 전체 빌드와 프론트 검증·독립 리뷰 후 격리 `.env`의 내부 소유자를 지정한다. 원본 스택이나 실제 주문은 건드리지 않는다. (프론트 `npm run build` 미실행, e2e 실제 실행·커밋 안 함)

빈 DB의 최초 비밀번호 설정·암호 변경 화면, 기존 비소유자 행·DB 컬럼 삭제는 이번 작업에 포함하지 않는다.
