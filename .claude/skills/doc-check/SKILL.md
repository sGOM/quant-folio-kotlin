# 문서 점검

설계 §4.4 의 주기 점검 절차(규격도 §4.4). 순서대로 한다.

1. **린트:** `node .claude/hooks/md-lint.mjs` → 0건이 될 때까지 고친다.
2. **낡음·모순:** 사용자에게 `/doctor prompt-audit` 실행을 요청하고 지적을 반영한다.
3. **일괄 최신화:** 마지막 `docs(claude)` 커밋 이후 `git diff --stat <그 커밋>..HEAD` 로 바뀐 코드 영역을 보고,
   그 경로에 `paths` 로 묶인 rules 본문을 코드와 대조해 틀린 서술을 고친다.
4. **커버리지:** 이번 단계에서 만든 코드 영역마다 `paths` 로 묶인 rules 문서가 있는지 확인. 없으면 만든다
   (원본 `sGOM/quant-folio` 의 해당 rules 문서를 *내용 출처*로, 형식은 이 저장소 규칙대로).
5. **교정 회수:** 이번 단계 대화의 교정과 auto memory 의 `feedback` 항목 중 저장소 공용 교훈을
   해당 rules "함정" 절로 옮긴다(옮긴 memory 는 지운다).
6. **판단 리뷰:** 이번 단계에 바뀐 문서를 서브에이전트(`Plan` 타입 — Edit·Write 는 없지만 Bash 는 있다)에 맡기고,
   프롬프트에 "파일을 수정하지 말 것"을 적는다.
   작성한 세션의 추론을 안 본 눈이 목적이다. 프롬프트에 아래 기준만 주고 문체 지적은 금지한다.
   - **강제 누락:** 예외 없는 규칙이 문서로만 있고 테스트·훅이 없다 → 테스트 초안(grep 패턴 등)까지 낸다.
     반대로 선호에 불과한 훅은 삭제를 제안한다.
   - **코드로 알 수 있는 줄:** 같은 내용의 코드 위치를 근거로 댄다. 왜·함정·원본 차이·금지 사유를 담은 줄은 제외.
   - **파일 간 중복:** 표·목록에서 같은 사실이 두 문서에 있다(md-lint 는 산문 문단만 본다).

   지적은 사용자 승인을 받은 것만 반영한다(서브에이전트는 사용자에게 묻지 못한다).
7. **사용량 점검:** `md-refine` 스킬을 실행해 세션 기록상 안 쓰인 문서·절을 찾아 삭제/병합/분리를 제안받는다.
8. 변경을 `docs(claude): …` 로 커밋.
