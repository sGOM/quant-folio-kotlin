# 9단계 컷오버 Runbook

**전제:** 8단계 완료, CI 녹색. 소유자가 실행 시점을 정한다(원본 매매가 멈춘다). 모의투자라 정지 허용(설계 §1).
**되돌리기:** 10단계까지는 언제든 Kotlin 스택을 내리고 원본을 다시 올리면 된다 — 단 Flyway baseline 이후 원본은 `flyway_schema_history` 테이블을 무시하므로 영향 없음. 원본은 `closed_at` 을 무시하고 종결된 partial 을 다시 정합한다(체결 기록에는 영향 없음).

## 절차 (원본 저장소 = `$ORIG`, 이 저장소 = `$KT`)
1. **매매 중지 확인:** 미체결 주문이 없을 때(장 마감 후 권장). `$ORIG` 에서 `docker compose exec db psql -U quant -c "select count(*) from orders where status in ('pending','submitted','partial')"` → 0 이 아니면 정합 후 재확인. 단 주문번호 없는 submitted·partial 은 원본 정합이 다시 보지 않아 정합을 돌려도 0 이 되지 않으므로 `select id, status, symbol, qty from orders where status in ('submitted','partial') and coalesce(trim(kis_order_id),'')=''` 로 따로 확인해 수동으로 정리한다. 남긴 채 넘어가면 Kotlin 기동 직후 그 주문들이 critical 알림을 내고 해당 종목 주문이 보류된다. 추가 확인: `select count(*) from orders where price is null` → 0 이 아니면 주문가 없는 주문은 단가 불명 체결을 기록하지 않고 errors 로만 센다(수동 확인). 컷오버 직후 첫 정합 pass 에서 주문일이 지난 미종결 주문이 한꺼번에 종결될 수 있으니 직전·직후에 `select id, status, created_at from orders where closed_at is null and status in ('pending','submitted','partial')` 로 대조한다.
2. **백업:** `docker compose -f $ORIG/docker-compose.yml exec -T db pg_dump -U quant quant | gzip > backup_precutover_$(date +%Y%m%d).sql.gz` — 파일 크기·`zcat | grep -c "CREATE TABLE"` 확인. 볼륨 스냅샷도 권장: `docker run --rm -v quantfolio_pgdata:/v -v $PWD:/b alpine tar czf /b/pgdata.tgz -C /v .`
3. **시크릿 이전:** `$ORIG/secrets/*.txt` → `$KT/secrets/`(13개, 특히 `credential_enc_key.txt` 동일해야 DB 자격증명 복호화). `.env` 는 `$KT/.env.example` 기준으로 값만 옮긴다(`KIS_ACCOUNT_NO`·`KIS_HTS_ID`·`KIS_ENV`·쿠키·포트).
4. **원본 앱 중지(DB·Redis 유지):** `cd $ORIG && docker compose stop web engine worker frontend proxy`.
5. **Kotlin 기동:** `cd $KT && docker compose up -d --build` — 같은 프로젝트명 `quantfolio` 라 기존 `db`·`redis` 컨테이너·`pgdata` 볼륨을 이어받는다. web 이 Flyway baseline(V1) 후 healthy.
6. **스모크:** `curl -s localhost:8080/health` → `"status":"ok"`, `cd frontend && E2E_BASE_URL=http://localhost:8080 npm run test:e2e`, 기존 계정 로그인·전략 목록·포지션 화면 확인.
7. **엔진 확인:** `docker compose logs engine | grep "운용 중 전략 복구"`, `redis-cli smembers engine:active_strategies`, heartbeat. 장중 첫 틱의 주문·체결 정합을 지켜본다. 새 알림 코드 `order_not_sent`·`order_number_recovered`·`order_closed_unconfirmed`·`order_fill_mismatch`·`order_unresolved`·`order_modified_externally`·`order_resolved_manually`·`order_resolve_rejected` 의 소비처(프론트·텔레그램)도 확인한다. 확인됨(2026-11-16, KIS 모의): 체결통보 13번 필드 `CNTG_YN`(접수·정정·취소 1, 체결 2), 분할 체결의 `CNTG_QTY` 는 건별(그래서 통보는 정합 트리거로만 쓴다), 주문일 주문 목록(`VTTC0081R`, `EXCG_ID_DVSN_CD=ALL`)이 행을 돌려주고 마지막 `tr_cont` 는 E, `ord_tmd` 는 접수 시각, 정정·취소 행 `orgn_odno` 는 원주문 `odno` 와 같은 10자리 표기, 단건 체결조회는 `VTTC0081R`+`ODNO` 로 행이 온다(`VTTC8001R` 은 빈 응답), 모의 WS `ws://…:31000/tryitout` 구독 성공. 남은 확인: 실전 WS 주소(`ws://ops.koreainvestment.com:21000/tryitout`)로 접속·통보 수신이 되는지(`체결통보 구독 user=…` 뒤 재연결 경고가 없는지) / 체결통보 직후의 단건 조회가 그 체결을 이미 포함하는지(로그 `체결통보로 주문 정합 … 결과=` 의 filled·partial 과 통보 수량을 대조 — 포함하지 않으면 60초 주기 정합이 잡는다) / 주문일이 지난 미완료 주문이 다음 날 종결(`closed_at`)되는지 / 토스 실응답이 `{"result": …}` 봉투인지, `status` 값이 무엇인지(`Fill.terminal` 은 FILLED·CANCELED·REJECTED 만 종료로 본다). 주의: 원본 `.env` 의 `KIS_WS_URL_VTS`·`KIS_WS_URL_PROD`(값 `wss://…`)는 Kotlin 이 읽지 않는다(`quantfolio-core.yml` 에 매핑 없음) — 가져와도 새 기본값을 덮지 않지만, 주소를 바꾸려면 코드(`QuantfolioProperties.Kis`) 수정이 필요하다. KIS 항목은 엔진 없이 모의투자 확인 도구로도 본다: 환경변수 `KIS_PROBE_APP_KEY`·`KIS_PROBE_APP_SECRET`·`KIS_PROBE_ACCOUNT_NO`·`KIS_PROBE_HTS_ID` 를 두고 `cd backend && ./gradlew -q --console=plain :engine:kisProbe --args="notices 30"` 을 켜 둔 채 HTS 에서 주문한 뒤 `--args="orders"`·`"balance"`·`"order <주문번호> <종목코드>"` 를 실행한다(모의투자 전용 — 조회 명령은 읽기 전용이고 `buy`·`sell`·`amend`·`cancel` 은 모의투자 계좌에 실제 주문을 실행당 1건 낸다, 선택 `KIS_PROBE_TOKEN_FILE` 로 토큰 재사용, 사용법은 인자 없이 실행).
8. **관찰 1주:** 알림(critical)·`runner_failures`·체결 정합 리포트·야간 백업(`/backups`)·뉴스/스냅샷 배치.
9. **정리:** 원본 저장소 archive. `alembic_version` 테이블은 남겨 둔다(설계 §7).

## 2026-11-16 KIS 모의 실측

- 최신화한 원본 저장소의 자격증명으로 잔고·주문 목록 조회 성공. 원본 engine·worker는 중지 상태였다.
- 승인 범위는 003480의 시장가 1주 매수·매도. 대량 주문·정정·취소 실측은 제외했다.
- 11:39:30 KST 매수 접수: `ODNO=0000022464`(10자리), `KRX_FWDG_ORD_ORGNO=00950`, `ORD_TMD=113930`.
- 매수는 11:47:17에 1주·4,265원 체결(접수 후 7분 47초). 11:48:05 잔고에서 1주·평단 4,265원을 확인했다.
- 매도 `ODNO=0000022989`는 11:48:24 접수, 11:48:37에 1주·4,205원 체결. 11:49:11 잔고는 0종목,
  11:49:18 주문 목록에서 두 주문 모두 `tot_ccld_qty=1`, `rmn_qty=0`이었다. 실측 수신 프로세스는 종료했다.
- `VTTC0081R`은 실제 주문 행을 돌려줬고 `ord_tmd`도 `113930`, 원주문의 `orgn_odno`는 `0000000000`이었다.
  빈 목록과 1행 목록의 마지막 `tr_cont`는 `E`, 보유 1종목 잔고는 `D`, 빈 잔고는 `E`였다. 정정·취소 행의 번호 표기는 미검증이다.
- 접수 통보는 23필드이며 13번(`CNTG_YN`)=`1`, 12번(`RFUS_YN`)=`0`, 9번 수량=`0000000001`이었다.
  매수·매도 체결 통보는 같은 23필드의 13번=`2`였고 `KisFrames.parseFillNotice`가 수량·가격·방향을 정상 파싱했다.
  접수 통보의 수량은 체결 수량으로 쓰면 안 된다. 분할 체결의 누적/건별 수량 의미는 1주 시험으로 판정할 수 없다.
- 매수 체결 후에도 단건 조회 `VTTC8001R`은 빈 목록 → `Fill(filledQty=0)`이었다. 같은 시점의
  `dailyOrders`(`VTTC0081R`)는 1주·4,265원으로 반환해 서로 불일치했다. 단건 조회만으로 미체결을 확정하면 안 된다.
- 접수 통보는 설치된 Node `ws`로 수신했고, 11:45:35 KST에는 수정한 `kisProbe notices`의 JDK 구독도 성공했다.
  원본에서 옮긴 운영 기본 주소의 문제는 [접속 문제 기록](../../migration-notes.md#kis-실측에서-확인한-접속-문제-2026-11-16)을 확인한다.
- 검증: `:engine:test` 152건(실패·오류·스킵 0), 문서 린트·`git diff --check` 통과. 엔진을 기동한 통합 실매매·토스·다음 날 종결은 시험하지 않았다.

## 운영 중 수동 조치

**수동 정리.** `order_unresolved`·`order_unconfirmed`·`order_fill_mismatch`·`order_modified_externally` 알림을 받은 주문은 엔진 제어 메시지 `resolve_order` 로 정리한다. 종결하면 그 종목의 신규 주문 보류가 풀린다(`OrderExecutor` 의 접수불명·미완료 술어가 `closed_at is null` 을 본다).
1. 증권사 앱에서 그 주문의 최종 누적 체결 수량과 평균 체결가를 확인한다. HTS 에서 정정한 주문(`order_modified_externally`)은 원주문과 정정 주문의 체결을 합친 수량과 그 전체 평균가다.
2. 주문일(KST)이 지난 뒤 아래 명령을 보낸다(오늘 주문은 거부된다). `symbol` 은 그 주문의 종목코드이고 **JSON 문자열**이어야 한다(숫자로 치면 앞자리 0 이 사라져 형식 오류). 주문의 종목과 다르면 거부된다. `filled_qty` 는 최종 누적 체결 수량(0 이상 정수), `avg_price` 는 그 누적 체결의 평균가이며 새로 기록할 체결이 없으면 생략할 수 있다.
3. 결과를 확인한다. 응답 `(integer) 1` 은 엔진이 받았다는 뜻이고 `0` 은 구독자 없음(엔진이 떠 있지 않음 — pub/sub 이라 재전달이 없으니 엔진을 띄운 뒤 다시 보낸다)이다. 알림 `order_resolved_manually`(성공)·`order_resolve_rejected`(거부, 사유 포함)는 둘 다 warning 이다. 형식 오류·없는 주문은 알림 없이 엔진 로그 경고만 남는다. 필요하면 `select status, closed_at from orders where id = <id>` 와 `select coalesce(sum(filled_qty),0) from executions where order_id = <id>` 로 본다.
4. 거부되면 사유대로 고쳐 다시 보낸다.

```bash
docker compose exec -T redis redis-cli PUBLISH engine:control '{"action":"resolve_order","order_id":123,"symbol":"005930","filled_qty":3,"avg_price":"71200"}'
docker compose logs --since 5m engine | grep -E '수동 정리|잘못된 제어 메시지|수동 주문 정리 실패'
```

**주의.** 엔진은 입력값을 증권사에서 검증하지 않는다 — 보내기 전에 주문 id·종목·수량·평균가를 다시 확인한다. 누적을 실제보다 크게 넣으면 없는 체결이 기록되고, 작게 넣으면 실제 체결이 영구히 빠지며, 평균가가 틀리면 단가·평단이 왜곡된다. 이미 잘못 넣은 값과 기록을 줄여야 하는 경우(`order_fill_mismatch`)는 DB 직접 수정이 유일한 수단이고 그 도구는 없다(executions 행·포지션 수량·평단을 함께 고쳐야 한다).
